# 多维度分析（研究流程第 2 步）

本文件是 `docs/research/public-company-financial-research.md` 第 2 步的唯一正文。在第 1 步采集产出的基础上，对六个维度分别做深入分析，汇总为一份结构化数据文件。

- **输入**：第 1 步落盘的采集文件（`docs/model/financials—model-template.json` 结构）。
- **产出**：按 `docs/model/financials—analysis-template.json` 结构生成分析文件，落盘为 `research/companies/<company-id>/financials-analysis.json`（文件名固定，渲染层按名发现）。

## 第二步联网规则

默认禁止联网。六个维度 Agent 只允许读取：

- `research/companies/<company-id>/financials-collection.json`（第 1 步产出；可能已含 Evidence Agent 补写的 `evidenceAppendix`，见下）

第 1 步采集清单固定 10 个维度、不多不少（`docs/model/financial-model.md`），本步骤分析中常遇到清单之外的关键事实缺失，例如：

- Customer Retention
- Pricing Power
- NPS
- App DAU

这类缺失**不属于第 1 步职责范围，也不允许维度 Agent 自行联网搜索补**。发现时，维度 Agent 在本轮返回的 `dataGaps` 对应条目上追加 `evidenceRequest` 子对象（结构见下），该字段本轮先按 `unavailable` 收敛，不为等取证而中断整份返回——硬约束「只返回一个 JSON 代码块」不变，证据缺口只是 `dataGaps` 的一项，不是暂停信号。取证与续写通过下面的跨轮次流程完成，不在单次 Agent 调用内发生。

### 取证轮次（跨 Task 调用，由主会话驱动）

1. **第一轮分析**：六个维度 Agent 各自禁网跑，返回中通过 `dataGaps[].evidenceRequest` 携带证据请求。
2. **去重合并**：主会话汇总六份返回，把指向同一事实的请求合并为一条（例如护城河与生意本质都要 NPS，只发一条）。
3. **派单取证**：用 Task 工具启动**一个**后台 Evidence Agent，指令须包含：去重后的请求清单、数据截止时间、`docs/model/financial-data.md` 的来源优先级与双源规则。检索纪律——每条请求最多 2 次检索，同一信息点找到一个可靠来源即停（量化且影响估值判断的事实优先双源，定性描述类允许单源但必须注明出处与时点）；2 次仍取不到按 `unavailable + reason` 收敛，不换关键词恋战。**检索走 `docs/research/tools/web_search.py`**（用法与三条纪律见 `01-data-collection.md` 3.3 节；量化事实回一手时加 `--official <市场>`），工具失败（退出码 3）降级原生 WebSearch。**工具只返回来源原文片段，不返回结论——写进 `evidenceAppendix` 的数字必须是你从片段或 `--full` 正文里读到的原文数字，不是任何摘要给出的转述值。** 取到的事实追加进 `financials-collection.json` 的 `evidenceAppendix`（新增字段，不改动已有 10 个维度的既有内容，不触发第 4 步重新校验）。
4. **第二轮分析（只重跑受影响维度）**：主会话把更新后的采集文件带回给有未解决请求的那几个维度 Agent；未涉及证据请求的维度不重跑。
5. **轮次上限 2 轮**（与第 4 步「关键信息补全流程」的先例一致）：第二轮后仍取不到的事实，维度 Agent 按规范 `unavailable + reason` 定稿，不再发起第三轮取证。

### `evidenceRequest` 结构

挂在 `dataGaps` 条目下的可选字段，仅当缺口有可能被外部检索解决时才附加；确实不可得（未披露且行业惯例也不披露）的缺口按普通 `dataGaps` 处理，不写此字段：

```json
{
  "path": "moat.analysis.types[0].evidence",
  "reason": "缺 NPS 数据，采集清单 10 个维度不含该指标",
  "searched": "financials-collection.json 未见相关字段",
  "evidenceRequest": {
    "metric": "NPS 或同类客户满意度指标",
    "question": "该公司最新 NPS/客户满意度数值，来源与时点？",
    "whyNeeded": "支撑 stickiness 强弱结论",
    "priority": "high | medium | low"
  }
}
```

## 执行方式

**每个维度使用 Task 工具启动一个独立后台 Agent**（六个 Agent 可并行；Codex 端用可用的子代理能力等价执行）。给每个 Agent 的指令必须包含：

1. 第 1 步采集文件的相关内容（或其摘要）作为基础材料；
2. 数据截止时间与本维度的分析要点、追问；
3. 统一输出格式（见下节，**含返回形式与字段写法的硬约束，须原文带给 Agent**）——不接受自由体裁的返回。

Agent 职责：**只读**第 1 步采集文件（含 `evidenceAppendix`），基于其中的数据与来源完成本维度分析，不做任何网络检索。每条分析必须带数据与来源（名称 + URL + 时点），无出处的论断不接受；遇到采集清单之外的关键事实缺失，按上节格式生成 `evidenceRequest`，不自行搜索。

主会话职责：汇总六个维度的返回，检查格式统一、追问已答；驱动上节「取证轮次」——收集并去重 `evidenceRequests`、派单 Evidence Agent、合并结果、重跑受影响维度，最多 2 轮；凡涉及计算的数字（估值倍数、情景推算、增速、对比差值）一律用 `docs/research/tools/financial_rigor.py` 验算，禁止 LLM 心算，工具输出记入 `crossValidationLog`；最后按模板落盘。

## 统一输出格式

六个维度共用同一信封（与 `docs/model/financials—analysis-template.json` 对应），Agent 必须按此返回：

- `conclusion`：一句话结论，必须能被下方数据支撑；
- `analysis`：本维度专属字段（见各维度定义）；
- `inquiry`：`{ question, answer }`——**追问必须有回答**，只有在关键数据确实缺失时才允许答「数据不足」，且要写明缺哪个数据；
- `dataGaps`：缺失项 + 缺失原因 + 已查范围。

图表类内容（收入结构、趋势线）以结构化数据序列表达，渲染留给发布环节。

### 返回形式（硬约束）

**Agent 只返回一个 JSON 代码块，块外不写任何文字**——不写寒暄、检索过程、进度说明、免责声明、"以下是分析"之类的引导句，也不在块后附 Markdown 版摘要。自由体裁或半 JSON 半散文的返回一律视为未完成。

1. 顶层只有一个 key，取该维度在模板中的键名：`businessEssence` / `moat` / `inversion` / `management` / `industryTrend` / `valuation`；
2. 其值的结构与 `docs/model/financials—analysis-template.json` 里 `dimensions.<key>` **逐字段一致**：字段名、嵌套层级、数组元素形状都不改，不新增字段、不删字段、不改名、不合并；
3. 取不到的字段保留键名，值写 `{ "status": "unavailable", "reason": "缺失原因 + 已查范围" }`，同时在该维度 `dataGaps` 登记；未完成的写 `"__TODO__"` 而不是留空字符串；
4. 返回内容必须能被 `json.loads` 直接解析（双引号、无尾逗号、无注释、无 `...` 省略号占位）。

### 字段写法：分点 + 篇幅上限

两条同时成立：**超过 2 句 / 80 字必须分点**，且**每个字段有篇幅上限**——不许用"已经分点了"换取无限加长。

| 字段 | 篇幅上限 |
| ------ | --------- |
| `conclusion` | 1 句 / 60 字，不分点 |
| 每个序号点 | 60 字 |
| 一般叙述字段（`mechanism`、`basis`、`observation`、`reasoning`、`culture` 等） | 2–4 点 / 合计 240 字 |
| `inquiry.answer` | 首句判断 40 字内 + 2–4 点 / 合计 300 字 |
| 表格内短字段（`path`、`decision`、`outcome`、`test`、`similarity`） | 40 字，单句不分点（渲染在窄列里，长了会把表格撑成高塔） |
| `toolOutput` | 工具原始输出照录，不受上限约束，也不分点 |

超上限不是"删到达标"，而是信号：要么该并的点没并（两点在讲同一件事），要么该拆的内容没拆进模板里的数组。

| 约束 | 规则 |
| ------ | ------ |
| 超长即分点 | 叙述字段超过约 2 句 / 80 字，写成内嵌序号的分点：`"① 第一点。② 第二点。③ 第三点。"`（或 `1) 2) 3)`）。多于 5 点说明该拆进模板里的数组 |
| 单点单义 | 每个序号点只讲一件事，自带自己的数据与口径；点与点之间不写「与此同时也需要注意到」这类承上启下的连接长句 |
| 分点用序号，不用 Markdown | 渲染层按 `①②③…` / `1)` 切分，每点在网页上独占一行（`.prose-point`）——所以序号必须用这两种形式之一。`#`/`**`/`-`/表格竖线会原样漏到页面上，一律不写；`\n` 渲染层也当分点切，但 JSON 里可读性差，不作首选 |
| 该用数组的用数组 | 模板里已是数组的位置（`evidence`、`failurePaths`、`vsPeers`、趋势 `series`）一条一个元素，不塞进一个字符串；反过来**不要把模板定义为字符串的字段改成数组**——渲染层 `text()` 遇到数组只输出「—」，内容会整段丢失 |
| conclusion 保持一句 | `conclusion` 渲染为章节导语，固定一句话、不分点；要展开的论据放 `analysis` 对应字段 |
| 不写重复前缀 | 枚举与数值由渲染层拼进小标题（如「粘性 / 锁定 · 强」「过去 5 年 · 变宽」），叙述字段里不要再复述一遍「粘性很强，主要因为……」，直接从理由写起 |
| inquiry.answer 先给判断 | 首句直接回答问题（是/否/取决于什么），随后再分点给理由；不要用铺垫段落把答案埋在中间 |
| 枚举照抄 | 枚举字段只取模板给出的原文（如 `强 \| 中 \| 弱`、`存在 \| 不存在 \| 待验证`、`变宽 \| 稳定 \| 变窄`），不自造措辞、不加"偏强""基本存在"这类修饰 |
| 数字纯净 | 数值字段只放数字 + 单位（`"32.4%"`、`"1240 亿元"`、`"18.6x"`），不夹叙述；口径与计算方式写进相邻的说明字段 |
| 占位规范 | 「取不到 / 算不出」**只写完整占位对象** `{ "status": "unavailable" \| "not-applicable", "reason": "…" }`，绝不把 `"unavailable"` / `"not-applicable"` 当值写成裸字符串——渲染层对字符串原样输出，百分比列会拼成 `unavailable%`，校验也会把它当作「已填」。第 4 步写法闸门按 `[裸占位字符串]` 拦截 |
| 大数字缩写 | 百万以上的数值写成缩写字符串（`"230.51亿"` / `"23.05B"`），渲染层只加千分位、不猜量级；裸数字整串拼进页面，第 4 步写法闸门按 `[大数字未缩写]` 拦截。**不限于货币**：标了 `unit` 的计数类数值（股 / 辆 / 户 / MAU）过百万同样要缩写（❌ `{ "value": 204716202, "unit": "股" }` → ✅ `{ "value": "2.05亿", "unit": "股" }`）；只加引号不缩写（`"23051044345"`）在页面上没有任何区别，闸门一样拦 |
| 来源结构化 | 每个数据点用 `{ metric, value, asOf, source: { name, url } }`，来源不写在叙述句里；`url` 必须是可直达完整链接，不接受「见公司官网」「同上」「多家媒体」 |
| 时点与估计 | 日期统一 `YYYY-MM-DD` 或 `FY2025` / `2025Q2`；估计值 `value` 前置 `[估计]` |
| 序列化趋势 | 5年趋势、收入拆解、同行对比一律"每年/每项一个对象"，不返回 Markdown 表格、不返回段落式罗列 |

反例与正例：

- ❌ `"公司毛利率高于同行主要是因为先进制程占比高同时议价能力强并且折旧政策相对保守而竞争对手在成熟制程上价格战激烈导致其毛利率被压缩此外汇率因素也有一定影响。"`
- ✅ `"① 先进制程收入占比 62%，结构性拉高综合毛利率约 8pct。② 单一供应地位使涨价可转嫁，2025 年提价 5% 未见订单流失。③ 折旧年限 5 年、较同行保守 1–2 年，压低当期毛利但不影响趋势判断。"`

- ❌ `"grossMarginPct": "unavailable"`（5 年趋势表里渲染成 `unavailable%`，读者以为是数据错乱）
- ✅ `"grossMarginPct": { "status": "unavailable", "reason": "该年度年报未单独列示毛利行项目，已查 2021 年报与招股书" }`
- ❌ `"marketCap": { "value": 23051044345, "currency": "HKD" }`（渲染成 `23,051,044,345 HKD`）
- ✅ `"marketCap": { "value": "230.51亿", "currency": "HKD" }`

### 交付前自检 / 主会话验收

Agent 返回前逐项自检：JSON 可解析 → 字段名与模板一致 → **超过 2 句 / 80 字的叙述字段都已用 `①②③` 分点，每点单义且 60 字内** → **各字段未超篇幅上限**（`conclusion` 60 字、一般叙述 240 字、`inquiry.answer` 300 字、表格短字段 40 字）→ 字符串内无 Markdown → 模板中的字符串字段仍是字符串（未改成数组）→ 每条论断都有 `source.url` → 枚举值照抄模板 → `inquiry.answer` 首句直接给判断 → 缺失项已进 `dataGaps`。

网页端的分点断行由 `apps/web/app/companies/[company]/page.tsx` 的 `splitPoints` 完成：`①②③…` 与 `1)`/`1.`（句末之后）和换行都会被切成独立一行。序号写法偏离这几种形式，网页上就会退回成一整段——这是本节要求用固定序号符号的原因。

主会话收到返回后按同一清单校验；**不合格的退回原 Agent 重出，不在主会话手工改写补格式**——手工补格式会掩盖 Agent 的缺口，导致缺失项漏登记。

## 维度一：生意本质

分析要点：

- 用一句话定义这门生意的本质
- 收入结构拆解（结构化序列）
- 5年盈利能力趋势（结构化序列）
- 商业模式画布：一次性销售 vs 订阅/复购？硬件 vs 软件 vs 平台？
- 生态粘性/客户锁定强度
- 毛利率水平与同行对比，解释为什么高/低
- 经营杠杆分析

**追问**：这门生意好在哪？如果只能用一句话描述，是什么？

## 维度二：护城河评估

逐一验证五类护城河：

| 护城河类型 | 验证方法 |
| ----------- | --------- |
| 品牌/定价权 | 是否能在不损失销量的情况下提价？ |
| 转换成本 | 客户迁移到竞品的成本有多高？ |
| 网络效应 | 用户越多产品越好吗？ |
| 规模效应 | 规模带来的成本优势有多大？ |
| 技术/专利壁垒 | 技术领先几年？能否被复制？ |

分析护城河趋势：过去5年变宽还是变窄？未来5年预判。

**追问**：10年后这条护城河还在吗？什么能摧毁它？

## 维度三：逆向思考与风险清单

- 列出「这家公司可能失败的所有路径」（路径/概率/影响程度）
- 历史类比：找到历史上处于相似位置的公司，结局如何？
- 跨学科分析：用网络效应理论、技术采纳曲线、竞争博弈等模型交叉验证
- 偏误自查：叙事偏差、锚定效应、幸存者偏差
- 收集空方核心论点

**追问**：我最可能在哪里犯错？聪明人为什么会不买/做空这家公司？

## 维度四：管理层评估

- CEO/创始人关键决策复盘（时间/决策/结果/评分）
- 资本配置能力：研发回报率、并购成功率、回购时机
- 股东利益一致性：管理层持股、薪酬结构、减持记录
- 组织能力：团队稳定性、关键人才风险
- 企业文化特征

**追问**：如果CEO退休，这家公司还能保持竞争力吗？

## 维度五：行业与长期趋势

- 判断所在行业是否处于「文明级范式转移」
- 历史技术革命类比（蒸汽机/电力/互联网/AI）
- TAM增长曲线与天花板分析
- 公司在产业价值链中的位置
- 技术路线风险
- 客户/供应商集中度分析

**追问**：站在20年后回看，这家公司是「这个时代的标准石油」还是「昙花一现的3Com」？

## 维度六：估值分析

- 当前市场定价（关键估值指标）——**必须通过工具验算**
