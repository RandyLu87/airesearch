# 第 7 步：评估与反馈

**一轮**研究的最后一步——同一家公司之后还会被反复重研究，每一轮都各自留下一条记录。把本轮的机器指标与阅读评分合并成一条**研究评估记录**，把「最差的一处」登记成一条**缺陷记录**，然后重跑一次发布，让研究评估页立刻包含这次评分。

**不完成这一步，这次研究不算完成。** 所有靠自觉的记录机制都会在几周后荒废，所以它是完成标准的一部分，不是可选动作。

## 为什么需要这一步

前六步保证了单次研究的证据链可复核，但回答不了另一个问题：**这套研究方法本身是在变好还是变坏。**

第 4 步的完整性分不能承担这个职责——它衡量的是模板槽位的填写率，一句有出处的准确判断和一句模糊的套话得分相同；而且它在已发布的公司上长期贴在 9.7 以上，对方法的好坏没有区分度。它是合格的放行闸门，不是质量指标。

真正需要被长期观察的是五个维度：**正确性、依从性、自主性、成本、稳定性**。它们全都是代理指标——报告最终是给人读的，所以还有第六个、也是唯一的最终标尺：**阅读评分**。

判定标准：固定模型与固定任务下，其中至少一项显著提升、其余不回归、成本不显著变差，才算这次方法改动是改进。**任何一项回归都不算改进。**

## 谁在打分：阅读评分 Agent

第 5 步的成品页已经落盘、评估页已含上一轮基线后，阅读评分**默认由评分 Agent 完成，不逐题问操作者**（2026-09-06 起）：操作者不可能当场读完一整份自己刚亲手产出的报告再冷静打分——上一轮的每个措辞取舍还热在脑子里，评分跟着「自己写的东西」走而不是跟着「读者看到的东西」走。评分 Agent 是一个干净的读者：它没参与采集、分析、总结与修补，只读第 5 步渲染的成品页，天然站在读者视角；它读报告的成本只有主会话的几分之一，不需要操作者空出一段完整时间。

**评分 Agent 打分要趁热、只读成品、绝不看源 JSON**——分数评的是「读者看到的报告」，不是「作者写下的字段」。它读完报告**当场**返回评分，攒到几天后再补的分全是噪音。

两个例外走人工：

1. **离线补录**（`--rating-json` 给现成评分文件，测试也走这条）：不启动 Agent，直接落账；
2. **一次研究结束、需要即时收尾而操作者愿意自己答**：走交互式 `npm run research:feedback -- --company <company-id>`，逐题手打（工具保留人工路径，正常流程不主动走它）。

### 操作者的两问

**行为两问——「这次研究有没有改变你的仓位或关注列表」与「这家公司是否属于你熟悉的行业」——只有操作者本人能如实回答，评分 Agent 无从代答**，也不允许拿 false 冒充「没改变」（那等于把「没答」洗成「答了：没有」）。

- 正常流程：评分 Agent 返回后，主会话向操作者转述报告与 Agent 给出的分数，**当场问这两问**；操作者不答也可以，记录里写 `null`（未答），评估页「改变了仓位」的分母只算已答的行；
- 交互式人工补录：这两问**可回车跳过**，不再强制。

### 台账按评分源分开读

落账时记 `ratedBy: "subagent"`（评分 Agent）或 `"operator"`（人工），评估页的台账与缺陷清单按行展示「评分人」列。

**分数不能跨评分源横向比较，只能按同一评分源的时间序列读趋势**：操作者的分数长期贴在高位——上一轮刚亲手写下的句子，评分时很难再挑出刺来；评分 Agent 换模型或换 prompt 后必须重建基线，否则会把评分源的变化记成报告的变化。这与方法文里「换模型之后必须重建基线」是同一条纪律。

## 怎么跑

读完报告**当场**跑。攒到几天后再补的分全是噪音。正常流程先启动评分 Agent（第二步）拿到评分 JSON，再落账发布：

```bash
python3 docs/research/tools/research_feedback.py \
  --company <company-id> --rating-json tmp/<company-id>-rating.json
```

（交互式人工采集只在离线补录时用：`npm run research:feedback -- --company <company-id>`，不加 `--rating-json` 即进入逐题手打；正常流程不主动走它。）

命令依次做五件事：

1. 从 `research/evals/events.jsonl` 取本次研究的运行事件——校验轮数、是否一次通过、三份得分；
2. 解析会话日志，补 token 用量与投入时长；
3. 把评分 JSON（评分 Agent 产出）或交互式输入（人工补录）并入评估记录；
4. 写入 `research/evals/runs.jsonl` 与 `research/evals/defects.jsonl`；
5. 重跑 `npm run publish`，研究评估页随之更新。

## 第一步：找上一轮基线

同一家公司的最近一次研究评估记录在 `research/evals/runs.jsonl`（按其 `ratedAt` 取最新一条）；历史记录在它之前。评估页 `research/site/evals.html` 是同一份数据的另一种读法。这一条是评分 Agent 任务包的输入，也是评估记录里 `vsLast` 的唯一依据——没有它，「比上一份更好 / 差不多 / 更差」无从谈起。**上一轮有、本轮没有的缺陷若还在（如 still-open 的缺陷记录恰好属于同一家公司、同一症状），`worstPart` 应如实写明。**

历史缺陷台账 `research/evals/defects.jsonl` 是「这家公司历轮的失败清单」：本轮报告如果仍然犯着其中某一条，那是最严重的一类问题，`worstPart` 必须写上并 `defectStep` 归到对应步骤。

## 第二步：启动阅读评分 Agent

**使用 Task 工具启动一个独立的评分 Agent**（Codex 端用可用的子代理能力等价执行），指令必须包含：

1. 本次研究的公司名与产出文件路径：
   - 成品页：`research/site/companies/<company-id>.html`——评分对象，**必读**；
   - 上一轮基线：`research/evals/runs.jsonl` 中该公司的最近一条（无则说明这是首轮，`vsLast` 填 `same`，后面在备注里写明「无上一轮基线」）；
   - 缺陷台账：`research/evals/defects.jsonl` 中该公司的全部条目（无则说明本轮没有历史缺陷可对照）。
2. **评分 Agent 只读成品页，不读源 JSON**——`financials-collection.json` / `analysis.json` / `summary.json` 都不许读：分数评的是读者看到的报告，不是作者写下的字段；读源文件等于作者给自己打分。页面渲染不出来、读不到或明显是空壳时，如实说明并降低对应分数，不脑补内容。
3. 五个评分维度、1–5 分与每维的自问句（下表）；
4. 三个必填的非评分字段：`vsLast`（比上一份：`better` / `same` / `worse`）、`worstPart`（这份报告最差的一处）、`defectStep`（那处最差归属哪个步骤：`collection` / `analysis` / `summary` / `render` / `process` / `unspecified`）；
5. 评分纪律（见下节，**原样带给 Agent**）——尤其「最差的一处」的写法：具体到可修，不写正确的废话。
6. 返回单个 JSON，**不夹带散文与寒暄**，可被 `json.loads` 直接解析。
7. 评分 Agent 在 `subagentNote` 里写**过程上下文**（读了哪几份材料、上一轮基线是否找到、有无因为页面渲染问题降分），`notes` 留空——`notes` 是给人（操作者）改写的字段，Agent 不该用；自称（"我是 AI"）也不写进 `subagentNote`，评分来源由 `ratedBy` 字段承载。

### 评分纪律（带给评分 Agent 的原文）

- **你是替一个没有参与本次研究的操作者读这篇报告，不是作者自评**：只按读者看到的成品与页面上的数字给分，写作者的意图与源文件内容一律不算数；
- 五维各 1–5 分，1 = 很差，5 = 很好；没把握的维度如实给分并写进 `notes`，不为了好看往上抬；
- **绝不联网**，只评这一页上的内容；
- **「最差的一处」写法**：写**这一页上最具体、最该修的那一处**——读者会在哪里被卡住、哪个数字起疑、哪句结论没有支撑、哪段是正确而无用的废话。不写「整体不错」「个别地方可改进」这类正确的废话；真觉得没有一处明显的差，才写 `"worstPart": null`（这是合法结果）。`worstPart` 与 `defectStep` 要能对上：这一处差在哪个环节，就归哪个步骤；
- 判断「比上一份更好 / 差不多 / 更差」只看**成品页**：上一轮基线的结论、策略、表述与这一轮的成品页逐项对照，不靠印象；
- 报告已发布于 `research/site/` 是第 5 步的完成标准，不是可给高分的内容——**页面本身能打开是默认值，不构成加分项**；只有页面上实际呈现的判断质量才算分。

### 评分 Agent 的输出信封（`defectStep` 枚举从 `research_feedback.py` 的 `DEFECT_STEPS` 取）

```json
{
  "trust": 3,
  "insight": 4,
  "readability": 3,
  "actionable": 4,
  "density": 4,
  "vsLast": "better",
  "worstPart": "买入建议的前提是「2026H2 产能落地且良率达标」，但正文只写了预期没有给任何可核实的里程碑与观察方式。",
  "defectStep": "summary",
  "notes": "（Agent 不填，留给主会话转述后的操作者改写）",
  "changedMyPosition": null,
  "familiarIndustry": null,
  "subagentNote": "已读第 5 步成品页全文；上一轮基线未找到（首轮），vsLast 按 same 计；可信维度因页面某数字无来源标注扣分。"
}
```

`changedMyPosition` / `familiarIndustry` 是操作者两问，评分 Agent 一律返回 `null`——见上文「操作者的两问」。

## 阅读评分怎么打

五个维度各 1–5 分：

| 维度 | 问自己 |
| --- | --- |
| 可信 | 读完敢不敢照它做决定？有没有哪个数字让我起疑 |
| 洞察 | 有没有告诉我一件自己不知道、或没想到的事 |
| 好读 | 5 分钟能不能抓住要点 |
| 可执行 | 触发条件真的能照着盯盘吗，还是听着像正确的废话 |
| 密度 | 套话、重复、凑字数占多少 |

三个必填的非评分字段，它们比五个分数更重要：

- **比上一份同类报告（更好 / 差不多 / 更差）**。人对绝对分的标尺三个月就漂了，对两两比较却很稳。三个月前打的 4 分和今天的 4 分本来就不是一回事。
- **这份报告最差的一处是什么**。**这是整套机制里信噪比最高的字段**：五个分数一定会随习惯向上漂移直至饱和，「最差的一处」永不饱和；而且它写下来就直接是一条缺陷记录。如果只肯认真填一项，填这一项。

  **「暂时没发现」是合法结果**，`worstPart` 写 `null` 即可，不会产生缺陷记录——强制每次都说出一处缺陷，只会逼出为了过校验而编的琐碎抱怨，把缺陷日志填成噪音。但它记的是一个明确状态（`noneFound: true`）而不是一段写着「无」的文本，且**「未发现」的比例会显示在评估页上**：长期偏高说明的多半不是报告变好了，而是这一项在走过场。

- **这次研究有没有改变我的仓位或关注列表**。行为指标比自评分诚实，无法自欺，且完全免费。（操作者两问之一，见上。）

还会记三个上下文字段：当时的 skill commit、所用模型、这家公司是否属于自己熟悉的行业。前两个用来把方法的改进与模型的变化分开——**换模型之后必须重建基线，否则会把模型的提升记成方法的提升**；第三个用来剔除「熟悉行业时更挑剔」造成的系统性偏差。（熟悉行业一问也是操作者两问之一。）

## 第三步：主会话落账

1. **转述与两问**：向操作者汇报本轮结论、评分 Agent 给的五维分数与「最差的一处」，当场问行为两问；
2. **补模型名**：评分 Agent 产出 JSON 的 `model` 键是给记录留的上下文位，值由主会话用本次研究的真实模型名填上（写模型名本身不用 Agent 判断）；
3. **落账**：评分 JSON 连同两问答案落盘为 `tmp/<company-id>-rating.json`，然后：

```bash
python3 docs/research/tools/research_feedback.py \
  --company <company-id> --rating-json tmp/<company-id>-rating.json
```

命令默认带发布：合并机器指标与评分 → 写 `runs.jsonl` 与 `defects.jsonl` → 重跑 `npm run publish` 让研究评估页包含这次评分。`--no-publish` 只写记录不发布；`--transcript-dir` / `--transcript` 在会话日志自动识别失败或补录历史研究时显式指定。评分 JSON 放 `tmp/`，一次性产物，不提交。

**评分 Agent 产出的 JSON 要人工过一遍**：机器落账前主会话有责任核对——五维分数在 1–5、`vsLast` 三选一、`worstPart` 要么是具体的一处要么为 null、`defectStep` 在枚举内。有不合规的直接退回评分 Agent 重出，不合规的评分 JSON 不会写入任何记录（工具退出码 2）。

历史研究补录（当时没有评估记录的公司）同样走这条：`--rating-json` + 无 `--transcript-dir`，成本字段记为 unavailable。

## 记录去了哪里

`research/evals/` 下三份**追加式、不追溯改写**的 JSONL。追加式是硬约束：历史评价一旦可以被后来的认知改写，纵向比较就不成立。

| 文件 | 谁写 | 内容 |
| --- | --- | --- |
| `events.jsonl` | 校验与合并工具自己写 | 每次运行一行：时间、公司、得分、退出码、skill commit |
| `runs.jsonl` | 本步骤 | 一次研究一行：机器指标 + 阅读评分 |
| `defects.jsonl` | 本步骤 | 每条「最差的一处」一行 |

两个来源的可靠性是分层的：**运行事件是一等事实**，校验轮数与得分都取自这里；**会话日志只用来补 token 与耗时**，它依赖编辑器的内部日志格式、会随版本变化，因此取不到时相应字段写空值并继续——记账的准确性让位于研究流程的健壮性，记账失败绝不允许阻断本步骤。

评估页把评分来源（人工 / 评分 Agent）按行展示。**分数按同一评分源的时间序列读趋势，不跨源横比**：同源自评的绝对分会系统性漂移，人工补录与评分 Agent 的记录混在一起平均，读不出任何东西。

## 缺陷日志怎么用

**改研究方法时，必须能指出这次改动修的是哪一条已记录的失败。** 没有对应缺陷记录的改动是凭感觉，不该进。修完回到那条记录上标注是否复现。

「缺陷率按类别随版本下降」本身就是最好的趋势图，而且比五项评分的均值可靠得多。

## 完成标准

- `research/evals/runs.jsonl` 新增一行，机器指标与五项评分齐全；
- `research/evals/defects.jsonl` 新增一行，症状是本次「最差的一处」原文（`noneFound` 时不产生，属预期）；
- 研究评估页（`research/site/evals.html`）能看到这一行；
- `npm test` 通过。
