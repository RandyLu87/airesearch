# 驱动指标跨研究快照延续

## 状态

已接受，2026-08-03。

## 背景

网易云音乐是当时唯一拥有研究快照的公司。按 `compareResearchSnapshots` 的真实判定逻辑核对 2026-03-26 与 2026-07-31 两份快照：

- 标准指标 12 个同 ID，仅 `diluted-shares` 口径漂移，**11 个可比**；
- 驱动指标 4 个对 6 个，同 ID 的只有 `gross-margin`，而它 `periodType` 也变了，**可比数量为 0**；
- 最紧约束 3 个换掉 2 个。

ADR-0010 的双层指标模型在标准指标那层立住了，在驱动指标那层没有。跨研究快照比较商业模式驱动是本仓库的核心能力，实际产出却是零。

根因不在代码，在领域模型：`CONTEXT.md` 对驱动指标只有单份快照内的完整性要求，没有任何跨快照的生命周期条款；研究流程与快照契约的措辞（「选择 5–8 个指标」）本身就在鼓励每次重选；schema 只校验驱动数量下限，不校验与上一份快照的连续性。术语层面，「研究快照对比」承诺比较兼容指标，而「驱动指标」从未承诺任何东西会兼容。

## 决策

驱动指标一经确立即跨研究快照延续。

新研究快照默认继承上一份的驱动 ID、定义与全部口径字段，只更新观测值、趋势、阈值与证据。增加、移除或重新定义驱动必须在 `thesisChange.driverChanges` 中记录 `driverId`、变更类型与理由；重新定义口径还要求 `summary.businessModelChange` 升级为「机制变化」或「结构性变化」。

两侧同时施力：`npm run snapshot:new` 预填口径，使延续成为省力路径；`npm run snapshot:check` 强制申报，使不延续成为需要交代的例外。

`driverChanges` 是**可选**字段，因此契约启用前的快照仍然合法，`schemaVersion` 保持 `1.0.0`。

契约落地时已存在的快照通过一份**显式豁免清单**（`CONTINUITY_EXEMPT_SNAPSHOTS`，按 `<company.id>/<snapshot.id>` 列举）跳过可比性层，目前只有一条：网易云音乐 2026-07-31。刻意不用截止日期：按快照自身时间戳判断的日期门会让任何新快照只要回填一个早于门槛的 `--at` 就自我豁免。清单只能通过修改代码加入，是一个可评审的动作。

最紧约束适用同一精神但只产生警告，不阻断。

## 备选方案

**常驻驱动 + 本期观察双层模型。** 表达力最强，能容纳「这一期特别想看一下 X」的临时指标，避免临时观察被硬塞进常驻集。否决原因：需要改动 Zod schema、公司研究主页与研究报告的渲染、以及研究快照对比逻辑，成本远高于收益；且在延续规则从未被执行过的情况下，先引入一个更复杂的模型是本末倒置。若日后确实出现临时指标被误塞的证据，可再评估。

**保持自由重选，仅强制记录变更。** 改动最小。否决原因：实测已经证明「靠自觉」不成立——两份快照之间六个驱动换掉五个，且当时的契约文本已经要求在 `thesisChange` 说明变化。

## 后果

- 公司研究主页上的研究快照对比会逐步变得有信息量，但**不会立刻好看**：网易 2026-03-26 与 2026-07-31 之间的断裂是既成事实，会继续如实显示「不可比较」。改善从下一份快照开始。
- 换驱动的成本上升了。这是刻意的——它本来就应该是一个需要论证的动作。
- 豁免清单硬编码在校验器中。它是一次性的迁移边界，不是可配置项；向其中添加条目等于宣布又一段历史不再受约束，应当经由新的 ADR。
