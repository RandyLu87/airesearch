# 估值由引擎从声明式组件计算，并强制方法体检

## 状态

已接受，2026-08-03。

## 背景

改版前 `valuationScenarioSchema` 的 `earnings`、`method`、`valueRange` 三个字段全是 `z.string()`，没有任何数值校验；研究报告的估值图表用正则从这段散文里抠数字画柱子。

拿唯一一份带估值的快照验算（股数 2.10 亿，汇率 0.8612）：

| 情景 | 它自己写的方法 | 按这个方法算出来 | 快照里写的 | 偏差 |
| --- | --- | --- | --- | --- |
| 熊市 | 18–19 亿 × 10x | HK$99.5–105.1 | HK$105–115 | +5.5% / +9.5% |
| 基准 | 20–21 亿 × 11–12x | HK$121.6–139.3 | HK$120–138 | −1.4% / −1.0% |
| 牛市 | 22–23 亿 × 13–14x | HK$158.1–178.0 | HK$145–160 | −8.3% / −10.1% |

三个偏差方向都不一样，说明它们不是从一个模型算出来的，是分别写出来的。同一份快照的 `currentExpectation` 声称当前价对应 11.6x–12.3x，按其自身盈利口径实为 11.0x–11.5x。

汇率此前**在仓库里任何地方都没有记录**。它是从 `currentExpectation` 那句话反解出来的，而反解出的 ~0.915 与实际市场汇率 0.8612 相差 6%。

`actionZones` 五档同时重叠又漏：HK$120–125 同时属于「小仓观察区」和「合理价值区」，两者行动指令不同；HK$138–145 不属于任何一档。

方法层面的问题更根本。净现金 135.75 亿元折合 HK$75.1/股，占当前股价 **59.6%**，而三个情景里这笔钱一次都没出现过。正常化盈利剔的是递延税项、没剔利息收入，于是这 135.75 亿元是通过「利息收入 × 11.5 倍」被间接定价的。合并 P/E 是这家公司最不该用的方法之一，而没有任何机制会指出这一点。

## 决策

三件事同时落地。

### 1. 情景由组件构成，价值区间由引擎计算

作者填 `components`：每条是一个倍数项（指标区间 × 倍数区间）或一个面值项（金额，可带折价）。引擎做区间算术、除以汇率与股数，输出每股价值区间与价值桥。

`computed` 字段仍然写在 JSON 里，让快照保持自包含可哈希，但作者不能手写：schema 的 `superRefine` 重算全部结果并在不符时报错。JSON 没有只读字段，校验器就是只读性的实现方式。

组件模型足够通用：单条倍数项即传统 P/E 或 P/B；多条组合即 SOTP（分部倍数 + 现金面值 + 治理折价）。

`summary.fairValue` 必须等于基准情景的计算结果；`actionZones` 的边界由熊市与基准区间单调推导，只有行动文案可以手写，因此结构上不可能重叠或留空。反向估值（当前价隐含倍数）由引擎解出。

### 2. 汇率与股数必填且带证据

`valuation.fx` 必须记录货币对、数值、时点和**至少两条** evidence，沿用 ADR-0013 为参考价格定下的双源交叉规则。`valuation.shares.scale` 必须等于 `valueScale`——这是防止百万与亿差一个数量级的最省事办法。

### 3. 方法体检与升级提示

`packages/research-schema/src/valuation/rules.ts` 保存一组从快照自身事实自动计算的规则（净现金占市值、分部走势背离、连续盈利年数、股东回报覆盖率、客户集中度、金融业、周期业……）。触发的规则作者必须逐条回应；某条规则不建议把某方法当主方法而作者标记为 `adopted` 时，校验器报错。

`methodSelection` 同时记录**理想方法**与**实际采用的主方法**。两者不同时，`blockedBy` 必须列出缺哪些数据、为什么需要、去哪里取——这个列表直接渲染成页面上的「补齐这些数据可以升级估值」。

DCF 只作交叉验证，不进引擎。`metric-playbook.md` 明写「避免假精确 DCF」，而把五年收入路径、每年利润率、WACC 与终值全部塞进快照正是那条规则在防的东西。倍数族与 SOTP 是确定性算术，输入少、无法假精确，因此归引擎所有。

### 版本化契约

`schemaVersion` 从单一字面量改为 `1.0.0 | 1.1.0` 的判别联合。1.0.0 快照按原样解析，不要求新块、不跑引擎校验；1.1.0 起全部强制。

历史快照因此**一个字节都不用改**。回填它们意味着为几个月前做出的判断编造一个当时并未记录的汇率和市场份额分母——那是把今天的数字写进昨天的结论，违反 ADR-0002。

## 备选方案

**仍手写区间，校验器只验算并允许阈值内偏差。** 保留作者取整、加折价等人工判断的空间。否决原因：「可以手写 + 允许偏差」必然需要一个 `deviationReason` 字段，而那个字段会迅速退化成「取整」两个字——回到现状。取整和折价都可以表达成组件（折价就是组件上的 `discountPct`），不需要在输出端开口子。

**DCF 也完整结构化进引擎。** 透明度最高，能画出逐年现金流。否决原因：直接与 `metric-playbook.md` 冲突，需要另写 ADR 推翻；且每份快照多出几十个无法取证、无法校验、下一份还得全重填的预测数字。

**只强制「两法交叉 + 反向估值」，不建规则集。** 改动最小，收益也实在。否决原因：不回答「哪种方法最理想」和「该补什么信息」，页面上也不会出现升级提示；而现有快照恰好证明了作者不会自己意识到 59.6% 的市值是现金。

## 后果

- 云音乐本轮的合理价值区间由手写的 HK$120–138 变为引擎计算的 HK$121.6–139.3。这是**口径修正而非观点变化**：三个情景的盈利与倍数假设全部沿用上一份研究，只是第一次真正乘了出来。已记入 `thesisChange.valuation`。
- 熊市与牛市区间变动更大（99.5–105.1 与 158.1–178.0），因为原写法与其自身输入偏差最大。操作区间随之重推，重叠与缺口消失。
- 每次研究多一步 `npm run snapshot:sync`。它同时物化账本与重算估值，是幂等的。
- 汇率现在必须真去取。取不到就按 `AGENTS.md` 的规矩中止研究，不估。
- 云音乐的理想方法被标记为 SOTP 而实际采用 P/E，页面上因此长期挂着三项待补数据。这是准确的现状描述，不是缺陷。
