# 护城河升格为结构化对象，并强制绑定驱动指标

## 状态

已接受，2026-08-05。实现排期见 GitHub Issue。

## 背景

护城河在这个仓库里没有住处。它散落在四个地方：

| 位置 | 它承担的部分 | 缺的部分 |
| --- | --- | --- |
| `driverMetricSchema.dimension` 的「护城河」枚举（`index.ts:79`） | 标记某个驱动与护城河有关 | 不说明是哪一条护城河、哪一类 |
| `marketPosition` 商业化与规模双口径背离 | 竞争格局变化最早的可观察信号 | 只测份额，不测份额为什么守得住 |
| `constraints` 最紧约束 | 飞轮被什么卡住 | 约束是障碍，护城河是资产，两者不是一件事 |
| `sections` 散文 | 完整论证 | 每次重写，无法跨快照比对 |

`business-model-playbook.md:54` 的「规模效应与护城河」只是驱动树八个维度中的一行，给出的是候选指标清单（留存、份额、成本曲线、双边流动性、研发复用、议价能力）。它没有要求作者说出：这家公司真正起作用的护城河是哪几条、它作用在因果链的哪一环、正在变宽还是变窄、什么能摧毁它。

后果是**护城河判断成了唯一不可跨快照比较的长期判断**。`constraints` 有 `status`（改善/稳定/恶化/待验证），所以能观察瓶颈是否解除；`marketPosition.measures` 有 `trend`；`driverMetrics` 有 `trend`。偏偏「护城河是否在变宽」——长期价值研究里最需要跨期比的那一个判断——只以散文形式存在。

对照参考实现（`ai-berkshire/skills/investment-research.md:112-126`）：五类护城河 × 验证方法的固定表格，加「过去 5 年变宽还是变窄」，加「10 年后还在吗，什么能摧毁它」。它问的问题是对的，表格形态是错的——五行固定表格逼作者给每一类都填一句话，产出四条不存在的护城河。这与 `business-model-playbook.md:70`「不要机械加权打总分」防的是同一个病。

## 决策

`businessModel` 新增 `moat` 数组，长度 1–3。它是**声明**而不是打勾清单：只写真正起作用的那几条。

| 字段 | 要求 |
| --- | --- |
| `id` | 稳定 ID，供跨快照比对 |
| `type` | `品牌定价权` / `转换成本` / `网络效应` / `规模成本` / `技术与牌照` / `其他`；取 `其他` 时必须填 `typeNote` |
| `mechanism` | 它作用在 `causalChain` 的哪一环——一个位置，不是一个形容词 |
| `driverIds` | **至少一条，必须指向已声明的 `driverMetrics[].id`**；校验器检查引用完整性 |
| `trend` | `变宽` / `稳定` / `变窄` / `待验证` |
| `breaker` | 什么能摧毁它，必须写出可观察的前置信号 |
| `evidenceIds` | 至少一条 |

`driverIds` 那条强制引用是本 ADR 唯一真正的约束，也是它全部的价值。没有它，`moat` 只是又一个散文字段。有了它，一条护城河必须落在一个有定义、有 `definitionVersion`、有口径、有阈值、有证据、且跨快照延续的指标上——护城河因此继承驱动指标已经建立的全部纪律，包括「不能换尺子来迎合结论」。

而如果一条护城河找不到任何驱动指标支撑，那正是这次研究应该发现的事实：它可能并不存在。

`trend` 用「变宽/变窄」而不复用 `constraints` 的「改善/恶化」，因为护城河的宽度变化本身没有好坏方向——变窄是坏事，但一条护城河从「待验证」变成「稳定」也不是「改善」。

跨快照变动按 `constraints` 的先例处理（`analysis-template.md:129`）：`moat` 的增删只产生警告，不阻断。护城河被证伪或新护城河成型都是研究进展的正常结果，且 `moat` 没有 `definitionVersion` 之类的口径字段可比，套用 `driverChanges` 那套强制机制没有对应的检查对象。作者在 `thesisChange.thesis` 中说明的义务写在 `WORKFLOW.md`，由流程而非校验器承担。

字段本身在 schema 里可选，以兼容已发布快照。**新研究的必填由骨架哨兵实现**：`npm run snapshot:new` 生成的 `moat` 是 `__TODO__`，哨兵层会逼作者填。这是 `WORKFLOW.md:16` 已经在用的手法——可选字段 + 哨兵骨架，比 schema required 更适合渐进演化的契约。

## 备选方案

**照搬五类固定表格，每类必填。** 覆盖完整，无遗漏风险。否决原因：形式主义。五行表格的实际产出是四条不存在的护城河加一条真的，而读者无法区分。它与 `business-model-playbook.md:70` 直接冲突。

**只进方法论层，不动 schema。** 零契约风险，今天就能生效。否决原因：护城河趋势就仍然不可跨快照比较。散文字段每次重写，比不了——而「护城河是否在变宽」恰恰是这套框架最应该跨期追踪的判断。

**不新增对象，改为在 `driverMetrics` 上加一个 `moatType` 标签。** 改动最小，复用现有对象。否决原因：一条护城河通常由多个驱动共同支撑——转换成本可能同时体现在留存率和迁移成本上。指标上的标签无法表达「多个指标共同支撑一条护城河」，也没有地方安放 `breaker` 与 `trend`。

**把 `breaker` 归入 `risks`。** 少一个字段。否决原因：`risks` 记录的是已观察到的不利证据，走绿/黄/红分级与「下一期验证阈值」那套流程；`breaker` 是尚未发生的终局条件，分级对它没有意义。混在一起会让风险清单里出现一堆无法分级的条目。

## 后果

- 每份新快照多 1–3 条声明，每条强制引用驱动指标。找不到指标支撑的护城河会因此暴露，这是收益不是成本。
- 报告页新增护城河区块，呈现类型、趋势、breaker 与它引用的驱动；公司研究主页可跨快照显示 `trend` 变化，呈现方式与 `constraints` 一致。
- 已发布快照不回填，页面显示「本次研究未声明」，不用空字符串——与 ADR-0002、ADR-0017 一贯做法相同。
- 历史类比因此有了归宿。参照类推理（历史上处于同样位置的公司死于什么）成为 `breaker` 的推导方法，写进 `business-model-playbook.md`，不新增字段。一个类比既不是 `fact` 也不是 `calculation`，让它作为纯 `inference` 独占一个必填字段会稳定产出不可复核的比喻。
