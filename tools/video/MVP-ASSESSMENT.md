# 报告视频化 MVP 可行性评估（OWLL-49）

验证样本：`research/companies/us-bili-bilibili/financials-summary.json`
验证机器：Apple M4 Pro / 14 核 / macOS 26.5 / Node 22.22 / Python 3.14.3
验证日期：2026-08-28

一条命令跑完整条链路：

```bash
cd tools/video
npm run pipeline -- --company us-bili-bilibili -- --concurrency=10
```

## 1. 端到端耗时

计时由 `scripts/pipeline.mjs` 逐段记录，落在 `out/pipeline/<company>/run.json`。

| 阶段 | 冷启动 | 热跑 | 说明 |
| --- | --- | --- | --- |
| 文案生成 `script_gen.py` | 0.07s | 0.13s | 纯标准库拼接，不联网、不调 LLM |
| TTS 合成 `tts_batch.py` | 8.6s | 7.4s | 11 条分镜串行合成 176.7s 音频（约 21× 实时） |
| 视频渲染 `render.mjs` | 95.8s | 67.9s | 5375 帧 1080p30，`--concurrency=10` |
| **合计** | **104.5s** | **75.3s** | 成片 2 分 59 秒 / 12.4 MB |

冷热差全在渲染那一步：首次跑要打 Remotion bundle（Chromium 已由 stage 1 预下载，本次不含 ~150MB 首次下载）。**一条 3 分钟片子约 1 分半，产出/耗时比约 2.4:1**——比实时录屏还快，不是瓶颈。

渲染耗时与核数强相关，`--concurrency` 默认按 CPU 推断；14 核上给到 10 是实测较优值。

## 2. 单条成本

**直接现金成本 $0**，全栈免费且无 API key：

| 组件 | 成本 | 依赖形态 |
| --- | --- | --- |
| Remotion | $0（个人/小团队免费许可） | 本地 npm 包 |
| FFmpeg | $0 | `@remotion/renderer` 自带，不装系统 ffmpeg |
| edge-tts | $0，无 key、无配额文档 | **联网**调微软 Edge 朗读接口 |
| Chromium headless | $0 | 首次约 150MB 下载 |

隐性成本，实测口径：

- **本次跑通没有触发任何重试**，11/11 条分镜一次合成成功，TTS 8.6s 里没有退避等待。`tts_batch.py` 的 `--retries` 默认 3，限流真发生时每条最坏拖三次，属未验证路径。
- edge-tts 是**无官方 SLA 的非公开接口**，断网即全链路失败。这是唯一的外部依赖，也是唯一一个"成本为 0 但可用性无保障"的环节；已有 Piper（离线、MIT）备选方案，切换只需在 `scripts/tts_engine.py` 加一个引擎实现。
- 机器时间成本：3 分钟片子占满 10 核约 68 秒。批量 16 家公司串行约 20 分钟。

## 3. 质量评价

### 可用的部分

- **音画同步是硬的，不是碰运气**。对成片跑 `silencedetect`，10 个画面切点**全部**落在静音间隙内，没有一句话被切点截断。原因是换算方向定死了：帧数 = `ceil(音频秒数 × fps) + 留白`，画面永远 ≥ 音频，拼轨时每段补静音到帧量化时长，不存在累积漂移（画面 179.167s / 音轨 176.736s）。
- **不编数字**。解说词只转述 `conclusion` / `advice` / `condition` / `action` / `disclaimer` 原文，分数取 `confidence` 原值；`score` 为 null 时条形图只留灰轨、不画 0 分的条。信息保真度这条守住了。
- **控时可靠**。仓库内 16 家有 `financials-summary.json` 的公司，估时全部落在 120–180s 区间（148.6s–177.5s），本次哔哩哔哩成片实际 2:59。
- **中文朗读整体自然**，`zh-CN-XiaoxiaoNeural` 语调平稳，财报口播这种场景够用；数字、百分号、财报期（`FY2025` → 2025财年）经 `text_normalize.py` 改写后读得对。
- **可重复**。同输入两次跑，`out/script/*.json` 与 `props.json` 的 sha256 完全一致；edge-tts 两次合成 11 条音频**时长逐条 0.000s 差**，实测比契约要求的"除 TTS 非确定性外一致"还更强。

### 明显不足的部分

1. **英文残留会被中文音色逐字母念**。哔哩哔哩这条片子里 `unknownTokens = ['Bilibili', 'Inc', 'in', 'price']`——开场念公司全名 "哔哩哔哩 (Bilibili Inc.)"，策略卡里 "当前35.11x PE已 price-in 乐观预期" 的 `price-in` 都会走英文串朗读。管线不掩盖（进 manifest 的 `unknownTokens` 并打 stderr），但也没解决。
   全仓扫了一遍：16 家公司里 **15 家有残留**，合计 70 个不同 token，只有平安是干净的。多数是公司英文名与行业缩写（`ARR` / `SOTP` / `IaaS` / `capex`），AMD 最多，15 个。
2. **长江电力那条更严重：原报告的字段路径被念了出来**。`sh-600900-yangtze-power` 的 `advice` 原文里写着 `moat.analysis.trendNext5y'稳定'`、`valuation.inquiry.answer`，script_gen 忠实转述，于是解说会念 "moat 点 analysis 点 trend Next 5 y"，画面上也照样显示。这不是模板的 bug——是**上游报告写作规范的洞**：`advice` 是给人读的正文，不该内嵌字段路径引用。规模化前必须在研究闸门那侧堵住，或在 script_gen 里加一条"字段路径不进解说词"的过滤。
3. **画面是静态卡片，没有任何动效**。策略卡单屏停 37 秒（1122 帧）不动，是全片最难熬的段落。信息密度也偏高：一屏三句建议 + 触发条件，观众要么读字要么听讲，很难两者兼顾。
4. **维度理由被裁到只剩第一句**。控时阶梯第一步就砍掉了 86.5s 内容（`adjustments` 里如实记着），七个维度各只播一句结论。够用但偏薄——想讲透就得放宽到 4–5 分钟，或者拆成"速览版 + 详解版"两条。
5. **没有配乐、没有转场、没有封面图**。MVP 范围内本就没做，但它决定了这批片子现在只适合内部复核，不适合直接发平台。

## 4. 规模化前要补的坑

按"必须先解决 / 可以边跑边补"分两档。

**必须先解决（否则批量产出的是有瑕疵的成片）**

| 坑 | 现状 | 建议 |
| --- | --- | --- |
| 字段路径进解说词 | 长江电力已中招，念出 `moat.analysis.trendNext5y` | script_gen 加一条过滤（形如 `a.b.c` 的标识符串不进解说），并在研究闸门加检测 |
| 英文残留 | 15/16 家有，共 70 个 token | 词表补公司英文名与常见缩写；或给一条兜底规则：连续拉丁串按字母朗读 vs 直接丢弃，要有明确策略而不是现在的"原样喂给音色" |
| 缺 `financials-summary.json` 的公司 | 18 个目录里 2 个没有（`hk-1523-plover-bay`、`us-crcl-circle-internet-group`），管线 exit 2 明确报错 | 批量调度要能跳过并汇总，而不是整批中断 |

**边跑边补**

- **批量调度与失败重试**：现在是一次一家的单进程命令，没有队列、没有断点续跑。16 家串行 20 分钟可以接受，但 TTS 阶段的网络失败会让整条链路白跑——最小改动是让批量脚本按公司隔离失败、把 `run.json` 汇总成一张表。
- **渲染并发**：单机同时渲两家会抢核，实际不如串行。要提速得上多机或降分辨率（720p 可省一半）。
- **模板对数据形态的鲁棒性**：16 家全部 `props-only` 通过，空态（`score: null`）路径由 demoProps 覆盖，但**真实数据里目前没有一家触发空态**——这条路径只有假数据验证过，第一次遇到真缺失时要盯一眼。
- **产物存放**：`out/` 全部 gitignore，12.4 MB/条，16 家约 200 MB。批量化前要定一个产物去处（对象存储 / 制品库），不能堆在开发机上。
- **edge-tts 可用性**：接口挂掉就是全停。批量化时至少要有"失败自动切 Piper 离线引擎"的降级，而不是人工换 `--engine`。

## 5. 结论

**方案已验证可行，建议继续投入下一阶段，但先做一轮内容侧修补再批量。**

依据：技术风险已经清掉了——链路一条命令跑通、音画同步可测且 10/10 命中、耗时 75 秒/条、现金成本 $0、同输入可重复。这些都是当初立项时最不确定的点，现在都有实测数据。

**不建议现在直接开批量**，卡点不在技术栈而在内容质量：字段路径被念出来（长江电力）和英文残留（15/16 家）这两条，批量跑只会把同一个瑕疵复制 16 份。这两条都是小改动——一条过滤规则加一轮词表补充，预计半天到一天。

建议的下一步顺序：

1. 修字段路径泄漏 + 补词表（必须，先做）。
2. 写批量调度：按公司隔离失败、汇总 `run.json`、产物落到统一去处。
3. 再决定要不要投视觉打磨（动效、配乐、封面）——那是"能不能发平台"的问题，和"链路能不能规模化"是两件事，不该阻塞第 2 步。

一句话：**技术方案不用再验证了，继续；但把内容侧那两条修完再开批量。**
